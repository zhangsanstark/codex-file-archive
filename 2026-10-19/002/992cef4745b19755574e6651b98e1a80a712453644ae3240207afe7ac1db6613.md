# Jev 模型学习指南：理解、概率与软件决策

资料核对截至 **2026 年 10 月 18 日**。本文适合了解过大语言模型、希望进一步理解 Jev 的读者，不要求机器学习基础。

本文依据 TypeSafe 官方文档与独立研究整理，没有进行付费 API 实测。文中的虚构客服案例、示例输出和阈值计算均为教学示例；论文中的测量结果会明确标注来源。版本、价格和实验功能以核对日期为准。

**先认识 Jev。** Jev 是 TypeSafe AI 发布的模型产品，核心接口是：接收材料、问题和判断标准，返回选项、分数或概率，供软件直接使用。可以把它理解成一个具有自然语言理解能力、能够表达不确定性的判断函数。它适合嵌入软件的分类、筛选、路由和评分环节。[官方介绍](https://docs.typesafe.ai/introduction)

例如，一套客服系统已经收到用户消息，需要决定由哪个团队处理、优先级多高、是否补充信息。这些都是范围明确的小判断。Jev 的目标是让这类判断可以快速、重复地被程序调用。

TypeSafe 在 2026 年 9 月 15 日发布 Jev，把这类产品称为 **System One Model**。这个名称借用了《思考，快与慢》中快速、直觉式判断的说法；Jev 的名字来自经济学家 William Stanley Jevons。这些是命名背景，不能据此推断模型重现了人脑机制，也不能把“System One”当作已经公开、可以完整复现的一套网络结构。[首发公告](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

**从一个客服例子理解输入。** 假设用户发来消息：

> 我的订单被扣了两次钱，昨天反馈过，到现在还没人处理。

这段话可以成为 `state`，也就是待判断的材料。还可以补充订单状态和历史沟通，但材料需要真实、与问题相关。

一次调用主要围绕下面三个概念组织：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `state` | 判断所需的材料与背景 | 客户消息、订单记录、历史沟通 |
| `instructions` | 这道题具体问什么 | 哪个团队应当首先处理？ |
| `criteria` | 候选答案或评价标准 | 账单团队处理扣款；技术团队处理故障；其他团队处理剩余情况 |

这与人做选择题有些相似：State 是材料，Instructions 是题目，Criteria 是选项及其含义。选项描述不清楚，即使模型有能力理解材料，也可能无法按你的业务口径判断。[Choice 请求结构](https://docs.typesafe.ai/primitives/choice)

**再认识三个基础问题类型。**

| 类型 | 要解决的问题 | 返回结果 | 常见用途 |
| --- | --- | --- | --- |
| Choice | 在明确的候选项中选一个 | 选中的项、各项概率、`confidence` | 分派团队、主题分类、工具选择 |
| Score | 按有顺序的等级评分 | 等级概率、加权分数、`confidence` | 紧急程度、相关性、按标准评价质量 |
| Noul | 某个命题是否为真 | “是”的概率，范围为 0–1 | 是否提到退款、材料是否支持某句话 |

Choice 返回概率最高的选项，所有候选项的概率之和为 1。候选项最好边界清楚；如果可能遇到范围外的输入，可以设计“其他”或“信息不足”选项。这个兜底项仍需要评测，不能保证模型一定会在不知道时选择它。[Choice 文档](https://docs.typesafe.ai/primitives/choice)

Score 的等级需要提前定义。例如把紧急程度分为：0 表示不急，1 表示需要尽快处理，2 表示存在明确的紧迫时限。假设模型给三个等级分配的概率分别为 0.1、0.3、0.6，则返回分数为：

```text
score = 0 × 0.1 + 1 × 0.3 + 2 × 0.6 = 1.5
```

这个 1.5 是等级编号的概率加权平均。它不等于“有 75% 的用户很着急”，也不表示模型测量出了某种客观的连续强度。等级怎么定义，会影响分数的含义。[Score 文档](https://docs.typesafe.ai/primitives/score)

Noul 可以判断“客户表示此前已经反馈过”。例如返回 0.98，表示模型给“是”分配了 98% 的概率。若返回 0.05，则倾向“否”；接近 0.5 表示两者难分。不要把低 Noul 值一律当成低把握。[Noul 文档](https://docs.typesafe.ai/primitives/noul)

**把这些概念放进一次请求。** 下面是符合文档结构的简化请求体，用于理解接口；阅读它不需要实际调用 API：

```json
{
  "model": "jev-1.13.0",
  "state": "我的订单被扣了两次钱，昨天反馈过，到现在还没人处理。",
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "哪个团队应当首先处理这条消息？",
      "criteria": {
        "billing": "扣款、账单和退款问题",
        "technical": "软件故障、登录失败和接口异常",
        "other": "其他问题，或信息不足以归入前两类"
      }
    },
    "reported_before": {
      "type": "noul",
      "instructions": "客户明确表示此前已经反馈过这个问题。"
    }
  }
}
```

为了便于复现，这里固定使用一个版本号。实际接入方式及 SDK 示例见[官方快速入门](https://docs.typesafe.ai/introduction/quickstart)。

以下是**人为构造的简化输出，不是上述请求的实测结果**：

```json
{
  "answers": {
    "department": {
      "type": "choice",
      "choice": "billing",
      "probabilities": {
        "billing": 0.8,
        "technical": 0.15,
        "other": 0.05
      },
      "confidence": 0.7
    },
    "reported_before": {
      "type": "noul",
      "noul": 0.98
    }
  }
}
```

软件可以根据结果分派工单，把“此前反馈过”作为一个优先级信号。模型提供判断，最终流程仍由程序规则决定。

同一请求中的多个问题共享 State，分别并行、独立评估。B 问题不会自动看到 A 问题的答案。如果 B 确实依赖 A 的结果，应由代码处理依赖，必要时分成两次调用。增加问题仍会增加输入 token，不能理解成无限问题完全免费。[并行与问题独立性](https://docs.typesafe.ai/introduction)

**理解它与生成式大语言模型的关系。** 生成式模型通常逐个生成 token，形成文字、代码或 JSON；token 是模型处理内容的单位，不等同于一个汉字或一个单词。Jev 的接口围绕预先定义的判断空间，直接返回结果和概率，输入仍以 token 计费。

对“分到哪个部门”这种任务，省去自由文本生成、共享输入并并行回答多个问题，具有降低延迟与成本的潜力。实际节省多少还取决于输入长度、比较对象、任务拆分与服务条件。[官方机制说明](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

| 比较对象 | 常见做法 | 学习时应注意 |
| --- | --- | --- |
| 手写规则 | 根据关键词、字段和条件分支判断 | 明确规则适合用代码；复杂语义可能很难穷举 |
| 为特定任务训练的分类器 | 使用标注数据学习类别边界 | 固定任务上很有价值，但通常需要数据与维护 |
| 生成式大语言模型 | 根据提示生成答案，也可以分类和评分 | 能处理开放任务，分类能力同样需要评测 |
| Jev | 根据材料和标准返回受约束的判断及概率 | 重点考察准确率、概率质量、延迟与总成本 |

这张表是帮助选型的概念比较，不代表所有实现都符合一种固定模式。传统机器学习同样可以返回概率，零样本分类也早已有研究。例如 2019 年就有利用自然语言推断处理新标签分类的工作。[零样本文本分类研究](https://aclanthology.org/D19-1404/)

这里的“零样本”是指：使用者没有为了眼前这项分类任务，先提供一套标注样本专门训练它。它不表示模型从未接受训练，也不能保证模型的训练数据没有包含某项公开评测的内容。

我的判断是：Jev 值得关注的地方，在于把通用语言理解、受约束输出、概率和低延迟组合成软件服务。仅凭“能分类”或“能返回 JSON”，不足以判断它的技术创新和应用价值。

**关于 RLCD，目前能确定到哪一步？** RLCD 的全称是 Reinforcement Learning for Calibrated Decisions，即“面向校准决策的强化学习”。官方把它描述为预训练语言模型之后的一条后训练路线，目标是让模型给出决策和较可信的概率。[RLCD 说明](https://docs.typesafe.ai/introduction/machine-learning-primer)

可以把后训练理解为：模型先通过大规模训练获得基础能力，再通过进一步训练塑造它的行为与输出。RLCD 这个名字说明了官方希望优化的目标，但名称本身不是可复现的算法。

在本次查阅的公开材料中，没有找到足以复现 Jev 的完整网络结构、参数规模、训练奖励公式与数据配方。因此，不应断言它“完全不用 Transformer”“就是 BERT 加分类头”或“已经脱离语言模型”。这些判断需要额外证据。

**最值得学习的概念，是概率校准。** 假设模型对 100 道类似的问题，都给选中答案分配 80% 的概率。最后大约答对 80 道，才符合这组预测报告的概率；如果只答对 50 道，它就过度自信。

校准考察的是：一组预测报告的概率，与实际发生频率是否接近。这是统计性质，不能保证某个具体答案正确。准确率与校准程度也不是一回事：一个能力有限的模型，仍可能比较诚实地表达自己没把握。[概率校准研究](https://proceedings.mlr.press/v70/guo17a.html)

举一个极端的教学例子：对正负样本各半的二分类任务，模型永远输出 50% 的正类概率，可能在总体上符合这个发生频率，但几乎没有区分具体样本的能力。可见，好的应用需要同时关心判断能力和概率质量。

**Jev 的 `confidence` 又是什么？** 这个字段不能直接翻译成“这次答对的概率”。对于 Choice，官方按照所选项概率相对均匀分布的提升程度计算它：

```text
n = 选项数量
p_max = 最高选项概率

confidence = (p_max - 1/n) / (1 - 1/n)
```

三个选项中，最高概率为 0.8 时：

```text
confidence = (0.8 - 1/3) / (1 - 1/3) = 0.7
```

这解释了前面示例为什么同时出现 0.8 与 0.7。前者是模型分配给选中答案的概率，后者是按约定公式计算的指标；二者都不是外部验证结果。Score 的 confidence 还有不同的公式，会考虑等级距离。Noul 没有独立的 confidence 字段。[Confidence 精确定义](https://docs.typesafe.ai/confidence)

**阈值把概率变成流程选择。** 例如程序规定：只有所选答案概率达到某个门槛，才自动采用，否则交给人工或其他系统处理。这叫选择性预测：系统只自动接受一部分判断。

下面使用 100 条假设样本解释取舍，并假设这些概率在相应群体上完全校准：

| 样本数量 | 所选答案的概率 |
| ---: | ---: |
| 20 条 | 55% |
| 30 条 | 70% |
| 30 条 | 85% |
| 20 条 | 95% |

按照“概率大于等于门槛时自动处理”计算：

| 概率门槛 | 自动处理 | 交复核 | 自动处理中的预期错误 | 自动处理的预期准确率 |
| ---: | ---: | ---: | ---: | ---: |
| 50% | 100 条 | 0 条 | 23.5 条 | 76.5% |
| 70% | 80 条 | 20 条 | 14.5 条 | 约 81.9% |
| 80% | 50 条 | 50 条 | 5.5 条 | 89% |
| 90% | 20 条 | 80 条 | 1 条 | 95% |
| 100% | 0 条 | 100 条 | 0 条 | 不适用 |

以 80% 门槛为例，只接受概率为 85% 和 95% 的两组：

```text
预期错误 = 30 × (1 - 0.85) + 20 × (1 - 0.95) = 5.5
预期准确率 = (50 - 5.5) / 50 = 89%
```

小数表示重复类似实验时的平均预期，不表示实际会出现半条错误。该表没有计算复核环节的准确率；交给复核也不代表后续一定正确。

这些数值完全是教学假设，不是 Jev 的性能数据。真实系统中，高概率样本未必始终更可靠，需要用自己的数据验证。提高阈值也不能修复材料缺失、标签设计错误或数据分布变化。

**如何理解“零幻觉”和“类型安全”？** 如果只允许返回“账单、技术、其他”，限制输出集合可以避免模型编出一个不存在的第四个团队，但它仍可能把账单问题错分到技术团队。

因此需要分清三层正确性：

| 层次 | 要检查什么 | 错误例子 |
| --- | --- | --- |
| 格式与类型 | 字段、取值是否符合接口约定 | 应返回已定义类别，却返回自由文本 |
| 语义判断 | 判断是否符合材料与标准 | 双重扣款被分到技术故障 |
| 业务执行 | 后续动作是否满足业务规则 | 即使判断正确，也不应绕过退款额度与审批规则 |

TypeSafe 对“零幻觉”的论述建立在输出符合预定结构的保证上，不能据此推导出所有判断都正确。[官方解释](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

把安全审核交给模型，同样需要专门验证。2026 年 10 月 13 日的独立受控对抗研究，在 Jev 的审核与钓鱼邮件任务中仍发现误判和攻击绕过。这支持一个有限结论：有界输出本身不会自动解决提示注入和语义错误。[对抗评测](https://arxiv.org/html/2610.17820v1)

**独立评测提供了什么证据？**

| 研究 | 测得的结果 | 主要限制 |
| --- | --- | --- |
| 2026-09-29，37 个数据集评测 | 固定 Jev 1.13；346,009 次请求，主评测约 9.15 美元；32 并发下平均客户端延迟约 0.36 秒 | 对照模型未启用思考；只评估特定版本与模板，不能推出全面优于推理模型 |
| 2026-10-05，七项政治科学任务复现 | Jev 单请求中位延迟为 0.09–0.27 秒；比较异步 Batch 费用时，GPT-6 Luna 在七项中的六项更便宜 | 延迟测量来自特定地点和日期；批处理费用与在线即时响应对应不同使用需求 |

第一项研究的 Choice 概率整体表现出较好的校准，但数据集间差异明显。在 UNFAIR-ToS 条款识别任务上，使用训练数据调整阈值后，micro-F1 从约 0.50 提升到 0.75。这说明模型有区分能力，并不代表统一使用 0.5 门槛就能得到好的最终结果。[37 数据集研究及限制](https://arxiv.org/html/2609.37647v1)

第二项研究提醒我们：单次在线响应速度、异步批处理价格和最终准确率，要分别比较。需要快速交互时，低延迟很有价值；允许较长等待时间的离线标注任务，可能有更便宜的其他方案。[七项任务复现](https://arxiv.org/html/2610.06625v1)

以上研究都是近期预印本，应把它们当作可以检查方法与数据的证据，而非不受条件限制的定论。官方“193.6 倍快、444.6 倍便宜”的数字则来自特定工作流，官方也说明这些倍率可能处于实际收益的较高端。[官方评测条件](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

**怎样把它用到一个资料调研流程中？** 以下是设计示例，不是已经验证过效果的产品方案：

```text
收集文章及原始来源
        ↓
Jev 按明确定义判断主题、相关性、材料完整性
        ↓
程序根据分数与概率筛选、排序
        ↓
生成式模型阅读入选材料并撰写综述
        ↓
对重要结论与引用进行复核
```

这套流程的关键风险是筛选漏掉重要材料。因此不能只测“选进来的文章看起来是否不错”，还要测“真正重要的文章漏掉了多少”。这是召回率的思路。

泛泛地问“这篇文章可靠吗”，往往混合多个判断。可以拆成：是否提供原始来源、给定证据是否支持核心论断、材料是否与研究问题相关。模型只能根据输入和自身能力判断，不能通过一个 Noul 问题凭空验证没有提供的外部事实。

普通代码适合承担计算、日期比较、权限检查和硬性约束。1.13 的官方已知弱点包含数学计数、日期比较、多层间接推断等；不要因为模型接口方便，就把精确计算也全部交给它。[官方已知能力边界](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

**做一个小练习，比记宣传语更能帮助理解。**

1. 选择 100–200 条自己熟悉的中文文本，人工标注类别。这一规模适合学习，不足以证明生产级可靠性。
2. 写清每个类别的边界，先只做一个 Choice 任务。记录有歧义的样本，必要时调整题目或标签定义。
3. 把用来调整规则和阈值的样本，与最后测试的样本分开，避免对同一批样本反复优化后高估效果。
4. 在同一组测试样本上比较简单规则、一个生成式模型和 Jev。使用相同任务定义，同时记录各方案需要的处理步骤。
5. 改变自动处理门槛，观察自动处理比例与错误率如何变化。核查高概率错例，而不仅是低概率样本。
6. 固定版本、问题文本和评测数据，保存结果。换版本或换问题后，重新测量，不直接沿用旧阈值。

可以使用以下记录表：

| 指标 | 通俗含义 | 为什么需要 |
| --- | --- | --- |
| 准确率 | 全部判断里，答对多少 | 了解总体表现，但类别不均衡时可能误导 |
| 精确率 | 判为目标类别的样本里，真正属于该类的比例 | 看误报有多严重 |
| 召回率 | 真正属于目标类别的样本里，识别出了多少 | 看漏判有多严重 |
| 自动处理覆盖率 | 全部请求中，有多少被自动采用 | 看节省了多少后续处理工作 |
| 自动处理部分的错误率 | 被自动采用的判断里，错了多少 | 判断门槛是否合适 |
| 概率校准 | 报告的概率是否接近实际频率 | 判断这些概率能否支持流程决策 |
| 延迟与总成本 | 从发出请求到结果可用的时间，以及完整流程费用 | 判断是否满足实际应用需求 |

F1 是精确率与召回率的调和平均，用来综合观察两者；它不能替代对不同错误后果的分析。例如漏掉一篇关键资料与多读一篇无关文章，代价可能并不相同。

**阅读顺序可以这样安排。**

- 先读[官方 Introduction](https://docs.typesafe.ai/introduction)和[Quick Start](https://docs.typesafe.ai/introduction/quickstart)，把 State、问题类型与返回值对应起来。Quick Start 也提供不用写代码的 Playground 入口。
- 接着读[Confidence 文档](https://docs.typesafe.ai/confidence)，亲手计算一次三选一的 confidence，并解释为什么它不同于最高选项概率。
- 再读[37 数据集评测](https://arxiv.org/html/2609.37647v1)的方法与限制部分，练习检查对照条件和模型版本。
- 想补机器学习背景时，读[概率校准论文](https://proceedings.mlr.press/v70/guo17a.html)与[零样本文本分类论文](https://aclanthology.org/D19-1404/)，理解哪些概念早已存在，哪些是 Jev 的具体产品选择。

读完后，可以用三个问题自测：为什么合法选项仍可能选错？为什么 confidence 为 0.7 不等于实测正确率为 70%？为什么一个模型反应更快，却未必是离线批处理最便宜的方案？能结合自己的例子回答，就已经抓住这份文档的主要内容。
