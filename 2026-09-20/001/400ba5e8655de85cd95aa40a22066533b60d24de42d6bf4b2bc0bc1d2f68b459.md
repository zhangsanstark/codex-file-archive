# 版权合规竞品调研与方案讨论

第一轮研究，2026-09-20。目标是帮助用户与本分支讨论未来规划，方案确定后再带回原任务制作 PPT。当前不修改 PPT。

**讨论方向已更新：** 用户要求构建安全对齐中的完整版权审核体系，不以选择单点痛点为前提。当前主稿为 [版权风险安全对齐与审核整体方案](07_版权风险安全对齐与审核整体方案.md)。本文以下的厂商证据继续保留，原单点优先级及提问仅作为第一轮研究记录。

**本轮范围已经确认：风控可主导的规则、Skill、审核服务、版权库与评测。** 模型训练、微调、机器遗忘、版权采购及赔偿承诺只作协作边界，不列为当前主项目。

## 先说我的判断

现有输入、输出两侧防护的方向成立。下一阶段最值得建设的是：**让意图判断有明确的策略依据，让审核结果真正约束内容展示，让正常任务在受限之后仍能得到帮助。** 对图片，已有 IP 与公众人物检测，新增价值应围绕间接描述识别、误拦复核和成图语境判断，不能再把“建设图片审核”当未来项目。

我建议先推进三个相互配合的工作：结构化的意图与处置规则、全文/流式/会话覆盖核验、能同时衡量风险与正常使用的评测。版权库增加必要权利字段作为支撑，图片上下文复核先做离线验证。语义作品比对需要证明增量后再投入全量服务。

这个排序是基于现有能力和依赖的判断，不是厂商优劣排名。若内部基线显示最大问题不同，优先级应相应调整。

## 一、别家公开做了什么

下表刻意分清产品规则、公开技术和测试结果。全部于 2026-09-20 检索；详细版本、日期、适用范围及限制见分报告。没有做跨厂商同题实测，也没有调用付费 API。

| 厂商/产品范围 | 最有价值的公开依据 | 对我们的具体启发 | 不应推出的结论 |
|---|---|---|---|
| OpenAI 通用安全审核与图像服务 | 2025-10-29 公布按传入政策审核的 [gpt-oss-safeguard/Safety Reasoner](https://openai.com/index/introducing-gpt-oss-safeguard/)；2026-09-08 [Images 2.5 系统卡](https://deploymentsafety.openai.com/chatgpt-images-2-5/safety-evaluations)披露输入图文与成图审核 | 将政策规则作为明确输入，复杂样本按需复核；图片同时考虑请求与实际结果 | 不是版权专项识别效果证明，不知道其版权索引和人脸库实现 |
| Anthropic 消费端 Claude 与输出过滤 | 2026-09-01 的[公开系统提示词](https://platform.claude.com/docs/en/release-notes/system-prompts/claude-fable-5-1)包含拒绝后继续索取、描述性角色请求等规则；另有[输出过滤说明](https://support.claude.com/en/articles/10023638-why-am-i-receiving-an-output-blocked-by-content-filtering-policy-error) | 意图判断应带上下文，替代任务应明确；不能只看本轮名字和字数 | 消费端提示词不等同 API 默认规则，也不能从规则推断真实防绕过率 |
| Google Cloud Gemini 服务层 | [安全与内容过滤文档](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/capabilities/configure-safety-filters)，更新 2026-09-18，提供复现停止原因和输出过滤处理说明 | 将现有 REJECT/ACCEPT 进一步连接到应用侧解释、受控替代及再次审核 | 原因码不是完整作品库或自动授权核验，不能证明已经解决多轮累计 |
| Microsoft Azure OpenAI/Content Safety | [保护材料检测](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/content-filter-protected-material?view=foundry-classic)，更新 2026-02-27，明确英语范围；[流式文档](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/content-streaming)，更新 2026-09-08，区分审核后返回和异步返回 | 区分检测命中与实际展示；第三方检测必须先验证语言与覆盖，现有中文匹配不应盲目替换 | 不能把通用产品宣传当中文专项数据，也不能把追溯删除算作从未泄漏 |
| Qwen3Guard 开源安全模型 | [官方仓库](https://github.com/QwenLM/Qwen3Guard/blob/main/README.md)公开版权类别、分档分类及流式接口；[技术报告](https://arxiv.org/html/2510.14276v1)，2025-10，说明版权分类与地域适配的局限 | 可用作基线或审核组件候选；作品证据和地域规则仍应独立管理 | 不等于千问 App 部署架构，综合安全分数不等于版权检出率 |
| DeepSeek 在线服务和训练披露 | [中文用户协议](https://cdn.deepseek.com/policies/zh-CN/deepseek-terms-of-use.html)，2025-09-05，提及输入输出审查及权益投诉；[训练流程披露](https://cdn.deepseek.com/policies/en-US/model-algorithm-disclosure.html)描述数据治理 | 可参考输入输出审查和反馈治理的责任划分，训练治理单列 | 本次未找到足以还原其版权专项在线算法、阈值和效果的证据；信息少不等于没有防护 |
| Adobe Firefly/Content Authenticity | [自有模型来源与防护说明](https://www.adobe.com/ai/overview/firefly/gen-ai-approach.html)，页面未标统一日期；[素材使用偏好](https://helpx.adobe.com/creative-cloud/apps/adobe-content-authenticity/generative-ai-training-preferences.html)，更新 2025-09-02，涉及支持的参考图使用功能 | 如有参考图业务，可将可信的使用约束传入策略；权利来源与生成追溯分开管理 | 不能把来源凭证当版权证书，也不能将 Adobe 自有模型承诺套到所有合作方模型 |

可以明确得出的结论是：**有依据可借鉴的是多层控制与可执行的产品规则，尚无证据支持“海外统一严格、国内统一宽松”，也不能拿不同厂商的不同评测数字比较技术高低。**

## 二、建议的六个候选方案

完整设计包含衔接方式、前提、成本、验证和不确定性，见 [风控可主导的候选方案](05_风控可主导的候选方案.md)。

| 候选方案 | 比现有方案增加什么 | 风控可先交付什么 | 建议位置 |
|---|---|---|---|
| A. 意图识别与策略执行分开 | Skill 识别请求与上下文，可信地域/授权信息由业务提供，按版本规则执行，保留正常任务与替代路径 | 请求分类、处置矩阵、正反例及 Skill 离线验证；独立审核接口具备后再对接服务 | 近期能力主线 |
| B. 全文、跨段及会话覆盖 | 核验内容何时审核、何时展示；按作品记录会话内已释放片段，防止各轮单看都很少 | 覆盖清单、受控回放结果、放行要求与会话规则；网关改造需研发配合 | 先核验，发现缺口优先补 |
| C. 图片上下文复核 | 对间接角色描述、含混关键词及成图增加语境判断，保留已完成的 IP/人脸审核 | 离线样本与影子评测、规则允许调整范围 | 条件具备后在线试点 |
| D. 带权利状态的版权库 | 已有对象增加版本、地域、用途、授权期限和规则证据；应急规则可复核、可撤回 | 重点对象字段与维护流程，法务核验结论接入 | 与 A 小范围并行 |
| E. 重点作品语义复核 | 先检索候选，再核对具体表达，补充连续匹配的真实盲区 | 已确认漏检的离线实验，分别评估新增检出与误拦 | 第二阶段探索 |
| F. 专项评测与反馈闭环 | 同时报用户实际收到的风险、正常任务误拦、有用替代和成本，投诉/申诉经核验进入回归 | 冻结测试集、结果口径、策略/模型/库版本记录 | 所有试点共同基础 |

**近期推荐组合：A + B + F，D 提供最小支撑，C 先离线。** 这不是六个项目同时大规模立项。先通过 B/F 确认问题分布，再选择 A 或 C 的首个试点；E 暂不安排全量上线。

## 三、什么变化才算“更好的方案”

以下是目标行为示例，不是自动法律结论，也不是已经验证的系统表现。

| 用户情境 | 希望实现的改进 |
|---|---|
| 要一本受限书籍的整章 | 限制原文，提供有用摘要/分析，替代答案仍经输出审核 |
| 拒绝后改为每次索取一小段 | 结合该作品的会话状态处理继续提取，允许之后转为正常讨论 |
| 正常长回答后半段意外复现入库作品 | 后半段和跨窗口内容仍被检查，受限内容不因展示早于审核而漏出 |
| 使用角色名表达泛化创意 | 先区分实际需求和既定硬性规则，有条件复核含混请求，同时审查最终成图 |
| 用户说“我是作者，已授权” | 按未核验声明处理，不用自述替代可信授权记录 |
| 已核验授权允许特定地区、用途和期限 | 在许可范围内正常服务，并能解释为什么这次允许、另一次限制 |

## 四、调研后需要保留的边界

- 固定字数、歌词行数、匹配长度等是内部产品策略，不是法定统一安全线。[美国版权局 FAQ](https://www.copyright.gov/help/faq/faq-fairuse.html)
- 作品状态、具体使用方式和许可范围需要一起考虑，原著与译本等不同对象不能只靠同一个名称判断。[中国《著作权法》](https://www.ncac.gov.cn/xxfb/flfg/flfg_532/202103/t20210309_50530.html)
- 语义相似只能帮助发现候选风险。研究中的非字面复现指标不自动等于法律侵权，更不能把摘要与同题材创作一并禁止。[CopyBench](https://aclanthology.org/2024.emnlp-main.844/)
- 公众人物按相关权益策略单列，不使用“人脸版权”概念。图片既有检测能力已完成，未来增强的状态仍需准确标注。
- 当前 98.46% / 0% 保留为用户给定测试结果，缺少样本量和定义，不据此估计全量效果。512 tokens 的材料仅触发覆盖核验，不据此宣称现网漏洞。

## 五、下一步讨论建议

优先讨论一件事：**当前更想解决实际风险遗漏，还是正常使用误拦？具体最突出的场景是什么？** 如果暂时没有统一数据，建议用小范围基线评测帮助选择，而不是先承诺一套庞大架构。

其次确认 Skill 的接入形态：当前仅支持给生成模型注入规则，还是支持独立审核调用和结构化返回。两种形态都能先做风控工作，但可承诺的交付不同。

选定首个试点后，再把它写为领导能判断的目标、关键动作、依赖与验收标准。此时再回到 PPT 第三页，不必把全部研究细节塞进一页。
