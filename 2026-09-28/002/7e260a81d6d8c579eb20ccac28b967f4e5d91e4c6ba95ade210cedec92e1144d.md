**2. 每篇详细文档都有统一的内容标准**

每个专题尽量覆盖以下内容，按主题调整篇幅：

| 内容要回答的问题  |                             |
| --------- | --------------------------- |
| 学习目标与前置知识 | 学完后应该能做什么判断？需要先理解什么？        |
| 问题背景      | 业务为什么会遇到这个问题？最简单的做法有什么限制？   |
| 原理与机制     | 内部怎样运作？关键流程是什么？             |
| 使用方式      | 在 Java 项目中怎样使用？必要代码和配置如何理解？ |
| 方案比较      | 有哪些选择？各自适用什么条件，代价是什么？       |
| 边界与故障     | 超时、并发、重启、断网、部分失败时会怎样？       |
| 工程实践      | 如何配置、监控、排查、上线和迁移？           |
| 案例与验证     | 通过什么业务案例或实验验证理解？            |
| 架构决策      | 什么时候引入，什么时候升级，应该关注什么信号？     |
| 总结与资料来源   | 需要记住什么？哪些结论有版本限制？去哪里继续查？    |

涉及并发、调用顺序、故障切换的内容，会加入流程图、时序图或状态变化示例。

代码会用于解释关键机制，也会说明设计约束和验收方法，方便你以后交给 AI 实现。

**3. “详细”要体现在把问题讲透**

例如《分布式锁》这一篇，内容会从使用场景一直延伸到失败后的业务正确性：

- 业务为什么需要锁，能否通过数据库约束、乐观锁或幂等设计解决。
- 锁保护的资源和范围是什么，锁粒度怎么选择。
- 获取、释放、过期、等待、重试分别如何设计。
- 任务没有完成，锁先过期了，系统可能出现什么情况。
- 进程暂停、网络异常、故障切换时，需要分析哪些执行顺序。
- 自动续租解决什么问题，还有哪些边界。
- Redisson 等实现提供了什么能力，使用者仍需承担什么责任。
- 如何处理旧锁持有者继续执行的问题。
- 锁与数据库事务、业务状态、外部调用怎样配合。
- 如何设计实验，检查方案在竞争和故障下的行为。

涉及 Redlock 等存在争议或依赖特定假设的方案，会列出假设、不同观点及来源。

最终你应该能够判断：**这个业务需要保护的到底是什么，以及所选方案在什么条件下能够保护它。**

**4. 按“主笔—独立审校—修订—复查”执行**

你的多 agent 要求会落实到实际写作流程：

1. **主笔 agent 负责一个中间件。**先组织章节、查阅来源，再逐篇完成原稿，保持术语和案例连贯。
2. **另一位 agent 独立审校。**检查技术结论、版本、推导、代码示例、故障场景和资料引用。
3. **审校形成问题清单。**每项写明问题所在、依据、影响和修改建议。
4. **主笔修订，审校者复查关键问题。**尚不能确定的内容标明疑点，避免写成确定结论。
5. **我负责跨文档整合。**检查章节之间是否矛盾、是否重复，以及是否真正服务于架构设计目标。

会分批安排写作和审校。**另一个 agent 表示认同，只是审校过程的一部分；技术结论还需要来源、推理或实验支持。**

尤其重点核查这些容易出错的内容：一致性保证、数据丢失条件、原子性与事务、锁的有效范围、重试与重复执行、分片限制，以及性能数据的测试条件。

**5. 每篇都有总结，整卷还有总复习入口**

每篇末尾固定保留：

- **核心知识点**：学完必须记住的结论。
- **易错点与适用条件**：哪些说法容易被过度概括。
- **选型与设计检查表**：真正做项目时需要逐项考虑什么。
- **自测题或场景题**：检查是否能解释、分析和作出选择。
- **延伸阅读**：官方文档、源码位置、课程或工程案例。

整卷再提供一份快速复习文档，以及按问题查找的索引，例如“缓存数据不一致”“消息重复”“数据库增长过快”“接口偶发超时”，直接指向相关专题。

培训项目、开源实现、生产实践文章和实验结果，也会标明各自的来源性质、适用版本与证据范围。

这样，最终资料会同时具备三个入口：**从头学习的详细教材、恢复记忆的知识总结、面对项目时使用的架构设计检查表。**这套拆分和审校标准，也会应用到 MySQL、消息队列、搜索等其他专题。
